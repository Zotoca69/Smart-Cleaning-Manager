# Room mapping and map change detection — proposed revision v0.3
Refs: #3, [architecture](../ARCHITECTURE.md), [requirements](../REQUIREMENTS.md), [POC report](../poc/POC_REPORT.md), [gap analysis](../GAP_ANALYSIS.md).
Status: v0.3 proposed; prior v0.2 approved in PR #4. Owner authorized simplified recovery; revised G3 pending. Selective replay rejected to reduce complexity; restarting full scope may repeat vacuuming and mopping, including water consumption. Owner approved normalized name comparison (Ä1) in PR #4. Alternatives: strict raw equality (rejected for avoidable interruptions), normalized equality with warning (selected), automatic name-based remapping (rejected for ambiguous identity). Consequence: fewer typographic false blocks, residual geometry risk unchanged.
Scope: engine-neutral contract only. No engine, database, UI framework or deployment selection. All examples synthetic.

## Responsibility and information model
- Configuration owner approves local immutable baseline revisions; candidate discovery never grants approval. Store privately, version schema and baseline separately, atomic activation and rollback by explicit approval plus fresh validation.
- Baseline: schema_version, baseline_revision, robot_binding (local HA device registry ID plus separately validated integration/entity reference; feasibility of stable binding to be verified), maps (per robot map key, raw name, complete segment inventory of ID and raw name), area mappings (stable HA area ID, expected floor ID where configured, map key, nonempty set of segment IDs), approval metadata. Map and segment IDs are scoped to robot/map, not globally unique or guaranteed stable after remap. Floor ID is not a map ID.
- Example: synthetic robot R, map M, segments 101/102/103 with synthetic names A/B/C; area X maps to [101,102], Y to [103]. Another map may reuse 101. Unique binding key is (robot_binding, HA area ID); each binding targets exactly one map. Multiple areas on different maps form separate physical jobs; robot selection is explicit, never inferred from active map. No implicit cross-map command.
- Map key is a local approved identity linked to adapter locator (e.g. flag), not the flag itself; locator reuse with identical metadata may escape detection. Entity rename requires explicit reference reconciliation with unchanged device identity; no silent rebinding. Require unique area binding keys and robot/map keys, unique segment IDs within each map, valid HA area references, explicit floor consistency if configured, no duplicated segment ownership within a map in v0.1. Shared segment across multiple HA areas (N:1) is unsupported in v0.2. Unmapped inventory segments allowed but never implicitly scheduled. Validate nonempty targets and unsupported schema; never silently migrate or discard unknown required fields.
- Configuration interface presents discovered candidates, changes and diagnostics for owner confirmation; no particular UI assumed.

## Adapter and evidence
Logical operations: discover_inventory(robot) -> complete inventory or typed failure; resolve_active_map(robot) -> reliable active identity or unknown; resolve_areas() -> registry snapshot or failure; dispatch_segments(robot,map,ids,profile) -> accepted/rejected/unknown. These are proposed contracts, not existing API names.
Native Roborock get_maps returned a map flag, name and segment ID/name dictionary in the read-only observation POC 07 (2026-11-20, #3). This single-map observation does not establish complete multi-map coverage. Active map identity and freshness guarantees require separate validation; inventory listing is not proof of active map. A selected-map name alone is insufficient if ambiguous or stale. Native app_segment_clean via vacuum.send_command was exercised in POC 04D/06F; acceptance/app confirmation is not physical completion. Matter is not required. Evaluate reusable engine mapping interfaces before building an adapter; candidate engines are not yet acceptance-tested.
Record discovery time, source, success and completeness. Require a successful fresh observation for each execution attempt, no cached fallback on timeout, malformed payload or unavailable state. Unknown freshness blocks execution (FRESHNESS_UNKNOWN); known stale observations block with FRESHNESS_STALE; cached-only data without validated freshness semantics cannot authorize dispatch. Installed versions, stale-cache semantics and map switching support are open implementation validation items.

## Validation algorithm
1. Load one approved baseline revision; reject missing, invalid, unsupported or unapproved configuration. Resolve target logical areas against current registry and expected floor/binding.
2. Read current complete inventory and active map; reject unknown, malformed, duplicate identifiers, wrong robot or ambiguous identity. Require reliable complete map catalog and complete inventories for all configured maps, including inactive maps. If any cannot be established, block robot (INVENTORY_INCOMPLETE); feasibility is an implementation gate. Missing configured map with unambiguous scope blocks that map; unexpected maps block robot because identity allocation may have changed. Unknown active map blocks robot (MAP_UNKNOWN); ambiguous identity uses AMBIGUOUS_IDENTITY instead. For target execution, require correct active map; do not automatically switch in this increment.
3. Compare complete ID sets and names per stable matched ID, ignoring ordering. Added/deleted IDs, materially changed names, map rename or replacement => changed. For segment names only, Unicode NFC + trim + casefold equality permits raw spelling differences with NAME_NORMALIZED warning; preserve both raw names. Any normalized collision among segment names within a map (baseline or observed) blocks that map with AMBIGUOUS_IDENTITY even when IDs match. Map names remain strict. Never use names to remap IDs. A canonical ordered serialization/digest may accelerate comparison, not substitute for explicit diff or geometry proof.
4. If other configured map changed, invalidate jobs targeting that map; if scope/identity cannot be determined, block all affected robot jobs. New unexpected maps or ambiguous shared identities block robot pending review. Unmapped added segment on target map still invalidates target inventory.
5. Return VALID_METADATA or BLOCKED with machine-readable reason, baseline revision, affected scope and safe diagnostic. Return a set of all observed applicable reason codes with scope; do not infer additional failures solely from missing evidence after an earlier failure. warnings do not override blocks. Codes: NO_BASELINE (missing/unapproved), SCHEMA_INVALID (invalid schema or empty targets/duplicate ownership), DUPLICATE_BINDING, AREA_MISSING, FLOOR_MISMATCH, ROBOT_MISMATCH (device or unresolved entity binding), INVENTORY_UNAVAILABLE (integration unavailable), INVENTORY_TIMEOUT, INVENTORY_INCOMPLETE, INVENTORY_INVALID (malformed/duplicate IDs), FRESHNESS_UNKNOWN (freshness cannot be established), FRESHNESS_STALE (known stale), MAP_UNKNOWN (active identity unknown), WRONG_ACTIVE_MAP, MAP_CHANGED, SEGMENT_ADDED, SEGMENT_REMOVED, SEGMENT_RENAMED, NAME_NORMALIZED (warning), AMBIGUOUS_IDENTITY, BASELINE_CHANGED, GEOMETRY_REVIEW_REQUIRED, COMPLETION_UNKNOWN, TASK_IDENTITY_UNKNOWN, RECONCILIATION_FAILED, POLICY_BLOCKED, PAUSE_REJECTED, RESUME_REJECTED, REVALIDATION_REQUIRED, DUPLICATE_ATTEMPT, OUTCOME_UNKNOWN. Config/robot identity failures block robot; target-specific failures block target map/job; unknown scope blocks robot. Store detailed diagnostics locally; public reports redact installation data.
6. Geometry is not verified by metadata equality. Known remap/geometry edit, even identical metadata, invalidates approval until manual inspection and new explicit approval. Undetectable changes remain residual risk; do not advertise geometry detection. Before unattended deployment owner must accept residual risk or require a reliable independent map revision/geometry signal. No live commands authorized by this design.

## Execution and resume
Orchestrator resolves logical targets into explicit segment list using approved revision. Bind validation result to robot, active map, revision, target IDs and execution attempt. Serialize local configuration activation and dispatch per robot; immediately recheck active map/inventory and baseline revision before submission, discard stale result on delay or change. Exact freshness window and locking implementation are open; external app edits can still race, so absolute atomicity is not claimed. If state changes while cleaning, notify orchestration to evaluate safe interruption; do not invent device abort semantics.
Pause preserves the robot's internal progress; resume only the same positively identified retained paused task, with fresh baseline/map validation, presence/guest policy and no unresolved command outcome. Never issue generic start unless adapter semantics establish same-task resume. Explicit abort uses the adapter's verified return-to-dock or stop-and-dock operation and terminates the task only after verified termination; docking alone is not proof of abort (automatic recharge may preserve a task). Unknown outcome blocks new dispatch pending reconciliation. A later authorized new start repeats the full original task scope using fresh validation and explicit segments; no selective room reconstruction, no automatic restart merely because docked. If task identity is lost, block resume (TASK_IDENTITY_UNKNOWN); require explicit reconciliation before new start. On restart discard validation tokens and revalidate; do not assume retained task. Baseline change blocks resume pending explicit reconciliation; no reinterpretation of old IDs. Task-level completion must be verified; unknown completion is not success (COMPLETION_UNKNOWN). Duplicate attempts require idempotency. Robot owns progress; SCM owns task lifecycle. Pause duration, automatic docking, network interruption and reboot semantics require runtime verification.

### Reconciliation and command failures
Separate task lifecycle from cleaning outcome. Lifecycle values used by this contract: RUNNING (verified active), PAUSED (verified retained paused task), WAITING_RECHARGE (verified retained task during recharge), TERMINATED (verified or reconciled ended task), UNKNOWN (unresolved lifecycle). Outcome values: COMPLETED (verified successful completion), NOT_COMPLETED (verified incomplete or aborted cleaning), UNKNOWN (insufficient outcome evidence). Termination alone never implies COMPLETED. A fresh verified robot observation proving no retained task and readiness (idle/docked alone is insufficient), or explicit owner acknowledgement that the old task has ended plus fresh readiness verification with no contradictory active/retained-task evidence, closes the old task as TERMINATED with outcome UNKNOWN unless completion is independently established. Owner acknowledgement cannot override unavailable robot, contradictory evidence or unresolved in-flight commands. Record source, time and actor locally. Failed reconciliation keeps lifecycle UNKNOWN and blocks new dispatch/resume with RECONCILIATION_FAILED (robot). A positively identified retained paused task may instead return to PAUSED after reconciliation; resume still requires fresh validation and policy permission. COMPLETION_UNKNOWN blocks success reporting only after termination is established; it does not block a later authorized full-scope start. No routine manual acknowledgement when termination is verified.
For diagnostic classification, dispatch means start or resume, not pause or authorized abort. All listed validation and identity failure codes block dispatch within their defined scope until resolved, except NAME_NORMALIZED (warning), COMPLETION_UNKNOWN (outcome report only after verified termination), PAUSE_REJECTED and RESUME_REJECTED (command failure reports requiring state refresh and applicable gates before further dispatch). POLICY_BLOCKED prohibits start/resume, not a verified policy-required pause; T12n therefore permits pause but no start/resume. Policy denial returns POLICY_BLOCKED (job); remain paused, no automatic command. Explicit abort is a separate authorized transition. Pause rejection returns PAUSE_REJECTED (job), retains last verified state (not assumed current), alerts user and refreshes state; no compensating command. Pause/resume timeout or ambiguous response returns OUTCOME_UNKNOWN (job), alerts user and blocks further dispatch until reconciliation. Resume rejection returns RESUME_REJECTED (job), refreshes state, no new start; remain PAUSED only if verified. Auto recharge with verified retained task enters WAITING_RECHARGE, no SCM start/resume command while charging; observe subsequent state, alert if policy prohibits device-driven continuation and apply the verified pause policy upon observed cleaning. Ability to prevent unauthorized autonomous continuation is an implementation gate before unattended use. Revalidate map and baseline before same-task resume as for new dispatch.

## Open decisions and next increment
Until a verified termination signal is available, interruptions may require owner acknowledgement before further scheduled cleaning, subject to reconciliation readiness evidence. Validate this limitation against AF01 unattended scheduling before deployment; do not relax reconciliation gates. Establish retained-task identity, termination and task-level completion signals, verified abort adapter semantics, autonomous recharge/policy behavior and reconciliation readiness evidence as implementation gates. Evaluate Compose/Extend/Fork/Build mapping and dispatch capabilities, establish active-map, complete catalog and inactive-map inventory coverage, stable device binding and freshness semantics by read-only POC, decide local persistence/concurrency and manual geometry invalidation workflow. Establish runtime test harness and negative paths before any deployment. Design approval is not implementation or deployment approval. #3 remains open until functional acceptance and regression evidence are delivered.
